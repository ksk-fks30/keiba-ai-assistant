# GH Open PR Review

## 概要

ユーザーが「PRを作って」「PR出して」「pushしてPR」「既存PRを更新して」など、ローカル変更をGitHub Pull Requestとして公開する依頼をしたときに使う。

このスキルの目的は、PR公開時の運用を固定すること。実装、テスト、コミットメッセージは、そのリポジトリのAGENTS.mdや既存スキル、プロジェクト規約に従う。

## 必須ルール

- PRは常にOpen、ready for reviewとして作成する。
- 同じ依頼内でユーザーが明示しない限り、Draft PRを作らない。
- PR作成後、終了前にCodex自身がPR差分をレビューする。
- レビューで「直す必要がある」と判断した指摘があれば、その場で修正し、必要なチェックを再実行し、コミットして再pushする。
- 指摘を修正しない判断をした場合は、最終応答で理由を明記する。
- ユーザーが「PR作成だけ」と明示していない限り、PR作成直後に作業を止めない。

## ワークフロー

### 1. リポジトリ状態を確認する

PR公開前に、現在のブランチとworktreeを確認する。

- `git status --short --branch` を確認する。
- ベースブランチはリポジトリ規約、既存PR、リモート状態から判断する。
- 必要なら、プロジェクト既定のブランチprefixでfeature branchを作る。
- ユーザーの無関係な変更を戻したり上書きしたりしない。
- 無関係な変更がある場合、このPRに含めるファイルだけをstageする。

### 2. 公開前チェックを行う

初回pushとPR作成の前に、可能な範囲でリポジトリ標準のチェックを実行する。

- `lint`、`typecheck`、`test` など、プロジェクトに定義された標準チェックを優先する。
- チェックを実行できない場合は理由を記録する。
- 自分の変更が原因の失敗はPR作成前に直す。
- ignoredなローカルデータ、認証情報、実レース成果物、ブラウザ状態、Cookie、`.env` を含めない。

### 3. コミットしてpushする

stageした変更を意図が分かる単位でコミットする。

- 有効なコミットメッセージ規約やコミット用スキルがあれば従う。
- 無関係な変更をコミットに混ぜない。
- ブランチをremoteへpushする。
- remote branchが既にある場合は、通常の更新pushを行う。

### 4. PRをOpenで作成する

GitHub Pull Requestを作成または更新する。

- 利用可能で認証済みならGitHub connectorを優先する。
- connectorが使えない場合は `gh pr create` や `gh pr edit` をfallbackとして使う。
- PRはready for reviewにする。`--draft` は使わない。もしDraftとして作成済みなら、続行前にOpenへ変更する。
- PR titleは簡潔にし、bodyには変更概要と実行したチェックを書く。
- 現在のbranchに対応する既存PRがある場合、重複作成せず既存PRを更新する。

### 5. PR作成後にCodexレビューを行う

PR URLができたら、CodexとしてPR差分をレビューする。

- 最後のcommitだけでなく、base branchとの差分全体を見る。
- バグ、挙動退行、データ損失、セキュリティ、プライバシー、入力検証不足、リスクに対するテスト不足、プロジェクト指示違反を優先して探す。
- 指摘は具体的なファイルと行を根拠に判断する。
- 好みの問題だけなら、リポジトリ規約違反でない限りblockingにしない。
- actionableな指摘がなければ、最終応答で「Codexレビューで修正必須の指摘なし」と明記する。

### 6. 必要な指摘を修正して再pushする

レビューで修正すべき点が見つかったら、同じbranchで対応する。

- 編集前に対象ファイルを必ず読み直す。
- 修正範囲はレビュー指摘に絞る。
- リスクがある変更ではテストを追加または更新する。
- 修正後、関連チェックを再実行する。
- ユーザーがamendやsquashを明示しない限り、修正は新しいcommitにする。
- 修正commitをremoteへ再pushする。
- PR本文やチェック結果の記載を更新すべき場合は更新する。
- 修正必須の指摘がなくなるか、ユーザー入力が必要なblockerに当たるまでレビューと修正を繰り返す。

## 最終応答

完了時は、次の情報を簡潔に伝える。

- PR URLと、Open / ready for reviewであること。
- branch名とpush済みであること。
- 実行したチェックと結果。
- Codexレビュー結果。修正必須の指摘なし、対応済み指摘、または意図的に残した指摘と理由。
- 残っているリスクや実行できなかった検証。

大きなdiffや長いコマンド出力は、ユーザーが求めた場合だけ貼る。
